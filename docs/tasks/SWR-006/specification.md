# Specification — SWR-006 AI Commander v0

## Business goal
Партия против AI становится живой: AI-сторона `core-v1` делает настоящие ходы (активации, перемещения, пасы) вместо авто-паса,
по тем же правилам и через тот же путь команд, что и человек, не подглядывая в скрытую информацию. По умолчанию играет бесплатный
детерминированный бот трёх уровней сложности; при явном включении — стратегия через OpenAI с откатом на бота при любом сбое и
бюджетом на партию. Это закрывает главный пробел продукта («AI не играет») и проверяет цикл blueprint §8.5 до усложнения правил.

## Фактическое состояние (проверено Analyst, 2026-11-19, `main` @ `c1ace26` = `7195758` + документ статуса)
- Движок `core-v1` (`packages/games/rebellion/src/rules/core/**`): раунд назначение→приказы→обновление; команды `ACTIVATE_SYSTEM`,
  `MOVE_PIECES`, `FINISH_ACTIVATION`, `PASS`, `ACCEPT_HANDOFF`; `coreLegalActions(state, viewer)` даёт **шаблоны** действий
  (`ACTIVATE_SYSTEM{leaderIds[], systemIds[]}`, `MOVE_PIECES{fromSystemId,toSystemId,pieces[]}` — любое подмножество с учётом
  вместимости, `FINISH_ACTIVATION`, `PASS`). `ctx.origin = 'auto'` разрешает команду только за AI-сторону AI-партии.
- Скрытая база: `coreSideView(state, 'empire')` до раскрытия показывает юниты/лидеров/активацию Повстанцев в базовой системе как
  зону `rebelBase`, `rebelBase.systemId = null`, события `SYSTEM_ACTIVATED`/`PIECES_MOVED` Повстанцев в базу/из базы — с `null`.
- Победа: Повстанцы — время достигло репутации (старт 1/14 → 13 раундов); Империя — база раскрыта (имперский наземный юнит в
  базовой системе в конце имперской активации этой системы) и в базовой системе есть имперский юнит и **нет** ни одного юнита
  Повстанцев (проверка после раскрытия и после каждого `MOVE_PIECES` любой стороны). На старте в базе 6 юнитов Повстанцев, боя нет —
  поэтому победа Империи над AI-Повстанцами возможна только если AI сам выводит юниты (PO-1).
- AI-сторона сейчас: `packages/games/rebellion/src/ai/auto-pass.ts` (политика `PASS`/`FINISH_ACTIVATION`) + `src/server/auto-play.ts`

- Платформа: `ServerGameModule` (`packages/platform/src/server-game-module.ts`) синхронный, без понятия автоматизации;
  `SessionCommandsService.execute` (`apps/api/src/sessions/session-commands.service.ts`) — 404→400→422→500→модуль→commit c
  `expectedVersion` (409 при гонке).
- AI-слой SWR-005B (`apps/api/src/ai/**`): `AiDecisionService` (mock/OpenAI, строгая схема `selectedActionId ∈ enum`, 2..10 действий,

  говорит «TEST scenario (not real game rules)», а `budgetKey` для dev ограничен `dev-diagnostics`. К партиям не подключён.
- Пакет `@bga/game-rebellion/ai` уже запрещён в web-бандле (`scripts/check-web-bundle.mjs`, `forbiddenGameModules`).
- UI: подписи `match.json` `autoHint`, `autoPass*` — «AI Commander ещё не реализован».

## Scenarios
1. **Человек-Повстанцы vs AI-Империя (бот).** Человек ходит; после каждой его команды сервер в том же HTTP-запросе выполняет ходы
   Империи (активация системы лидером → перемещения → завершение активации / пас), пока не наступит ход человека или конец партии.
   Ответ содержит события человека и AI (отфильтрованные для человека) и сводку автоматизации. UI показывает «AI ходит…», затем
   что сделал AI.
2. **Человек-Империя vs AI-Повстанцы.** Создание партии сразу выполняет первые ходы AI-Повстанцев. Империя не видит, где база и куда
   уходят юниты из базы (редактирование SWR-005 сохраняется). На easy/normal AI иногда оставляет базу пустой → Империя может
   победить; на hard AI всегда держит в базе ≥1 юнит.
3. **Сложность.** easy/normal/hard меняют поведение бота (а не только текст): разные правила выбора, измеримые на seeded-партиях.
4. **OpenAI-режим** (`AI_COMMANDER_PROVIDER=openai`, `OPENAI_ENABLED=true`): на каждом шаге бот формирует короткий список (≤ 10)
   конкретных кандидатов-команд из legal actions, модель выбирает id; сервер проверяет id и выполняет команду движком. Любой сбой
   (невалидный ответ, таймаут, 429, 5xx, нет конфигурации, бюджет партии исчерпан, превышен дедлайн хода) → этот шаг делает бот,
   партия продолжается; UI показывает «ход сделал бот: OpenAI недоступен» (без деталей).
5. **Прерванный ход AI.** Если цикл AI прервался (рестарт, гонка, лимит шагов), сессия остаётся «ожидает ход AI»; GET это сообщает,
   клиент вызывает идемпотентный `POST /api/sessions/:id/automation/run`, который доигрывает ходы AI.
6. **Hot-seat и старые партии** работают как раньше; mock-v1 партии не имеют автоматизации.

## Contract (заморожен до параллельной работы; поправки — через Analyst)

### 1. Платформа (`@bga/platform`, новый `src/automation.ts`) — game-agnostic, без слов Rebellion
```ts
/** Один конкретный вариант хода для автоматического игрока. */
interface AutomationCandidate {
  id: string;            // /^[a-z0-9-]{1,32}$/, уникален в decision point
  type: string;          // тип команды игры (непрозрачно для платформы)
  target?: string;       // ≤ 64, необязательно
  summary: string;       // ≤ 160, англ., ТОЛЬКО из представления актёра (идёт в промпт модели)
}
interface AutomationDecisionPoint {
  actor: string;          // непрозрачная сторона
  phase: string;
  objective: string;      // ≤ 300, англ., из представления актёра
  candidates: readonly AutomationCandidate[];  // 1..10, порядок = ранжирование бота
  fallbackCandidateId: string;                 // выбор бота, ∈ candidates
  policyId: string;                            // напр. 'rebellion-bot-v1:normal'
}
interface GameAutomation<State, Event> {
  /** Сторона, чей автоматический ход ожидается, или null (не AI-партия / ход человека / конец / другой движок). */
  pendingActor(state: State): string | null;
  /** Строится ТОЛЬКО из представления актёра (для Rebellion — toSideView(state, aiSide)). Детерминированно. */
  decisionPoint(state: State): AutomationDecisionPoint;
  /** candidateId → команда → полный конвейер игры (origin 'auto', expectedVersion = version(state)). Неизвестный id → ok:false. */
  applyCandidate(state: State, candidateId: string, ctx: ApplyCommandContext): ApplyCommandResult<State, Event>;
}
// ServerGameModule получает НЕОБЯЗАТЕЛЬНОЕ поле `automation?: GameAutomation<State, Event>`.
```
- Ответы API (generic, расширение схем платформы):
  - `SessionResponse.automation: { pending: boolean; strategy: 'bot' | 'openai' | null }` (`null` — у игры/сессии нет автоматизации).
  - `SessionCommandOk.automation: AutomationRunSummary` где
    `{ steps: number; pending: boolean; strategy: 'bot'|'openai'|null; fallbacks: number; stopReason: 'humanTurn'|'gameOver'|'none'|'stepLimit'|'conflict'|'error' }`.
  - Никаких кандидатов, причин модели, промптов, сумм бюджета в ответах игроку (только агрегаты выше).
- Новый эндпоинт: `POST /api/sessions/:id/automation/run` (тело пустое/`{}`) → `200 SessionCommandOk` (view + отфильтрованные
  события выполненных AI-шагов + `automation`); если автоматического хода нет — `200` с `steps: 0`, `stopReason: 'none'`.
  Идемпотентен (повтор не делает лишних ходов). Ошибки: 404 сессия, 422 игра недоступна.

### 2. Сервер: цикл автоматизации (`apps/api/src/sessions/automation/**` или аналог — решает BE-lead; game-agnostic)
- `AutomationRunner.run(sessionId)`: вызывается после успешного commit команды человека, после создания сессии и из эндпоинта `run`.
  Шаг: загрузить строку → `pendingActor` null → стоп → `decisionPoint` → стратегия выбирает id → `applyCandidate` → **отдельный commit
  на шаг** с `expectedVersion` (как у человека: `setupOf`, `statusOf`, события в `SessionEvent`) → повтор.
- Остановка: ход человека / конец партии; лимит шагов на запуск (`AI_COMMANDER_MAX_STEPS`, по умолчанию 64) → `stepLimit`;
  потерянная гонка commit (409) → `conflict` (тихо, другой исполнитель продвинул сессию); отказ движка на выбранный кандидат →
  повтор с `fallbackCandidateId`; отказ и на нём → `error` (лог 500-уровня, сессия остаётся `pending`, ответ человеку всё равно `200`
  с его принятой командой).
- Сериализация: один запуск на сессию в процессе (in-process mutex по `sessionId`); второй вызов ждёт/присоединяется и не дублирует
  платные запросы. Между процессами защищает оптимистичная конкуррентность.
- Ответ на команду человека = view после цикла + события человека + события AI (всё через `toPlayerEvents`, т. е. редактировано для
  человека) + `automation`. Ответ на `POST /api/sessions` — как раньше (`SessionResponse` c `automation`).
- Логи: одна строка на шаг — `sessionId, gameId, step, strategy, source(bot|openai), fallbackCode?, durationMs, code` — без
  кандидатов, команд, систем, причин модели.
- `rebellionServerModule` больше НЕ вызывает `runAutoPlay` внутри `applyCommand`/`createInitialState`; авто-пас и `runAutoPlay`
  удаляются или остаются только как тестовый хелпер (решает BE-lead). Миграция данных не нужна: в БД нет сохранённых состояний «ход AI»
  (авто-пас выполнялся тем же коммитом), а если появятся — их доиграет `run`.

### 3. Стратегии (`apps/api`, game-agnostic)
```ts
interface CommanderStrategy {
  readonly id: 'bot' | 'openai';
  choose(point: AutomationDecisionPoint, ctx: { sessionId: string; deadline: number }):
    Promise<{ candidateId: string; source: 'bot' | 'openai'; fallbackCode?: string }>;
}
```
- `bot` — возвращает `fallbackCandidateId` (бот живёт в игре, сервер его не знает).
- `openai` — если кандидатов < 2 → бот без вызова; иначе `AiDecisionService` с `budgetKey = sessionId`, роль `tactical` (по умолчанию,
  `AI_COMMANDER_MODEL_ROLE=tactical|strategy`), `availableActions` = кандидаты (id/type/target + summary), objective/phase/side из
  decision point. Промпт для партий — отдельные инструкции «board game AI commander» (не «TEST scenario»), поля — данные, не
  инструкции. Валидация id ∈ кандидатов (существующий `validateDecision`). Любой `AiFailure`/ошибка AI-кода, включая
  `AI_BUDGET_EXCEEDED`, или превышение дедлайна запуска (`AI_COMMANDER_RUN_DEADLINE_MS`, по умолчанию 45000) → бот,
  `fallbackCode = <код>`. Невалидный ответ не повторяется (как в SWR-005B). После исчерпания бюджета партии оставшиеся шаги — бот без
  обращения к OpenAI.
- Каждый вызов OpenAI пишет строку `AiUsage` (как SWR-005B) с `budgetKey = sessionId`; dev-эндпоинт по-прежнему принимает только
  `dev-diagnostics`.

### 4. Окружение (`apps/api/src/config/env.ts`)
| Переменная | Правило |
|---|---|
| `AI_COMMANDER_PROVIDER` | `bot` \| `openai`, по умолчанию `bot`; `openai` требует `OPENAI_ENABLED=true` (иначе старт не проходит, сообщение по имени) |
| `AI_COMMANDER_MODEL_ROLE` | `tactical` \| `strategy`, по умолчанию `tactical` |
| `AI_COMMANDER_MAX_STEPS` | целое 1..256, по умолчанию 64 |
| `AI_COMMANDER_RUN_DEADLINE_MS` | целое 1000..120000, по умолчанию 45000 |
- `.env.example` обновлён (тест-сверка из SWR-005B); тестовая среда — `bot`; в `NODE_ENV=test` `openai` работает только с fake fetch.

### 5. Бот Rebellion (`packages/games/rebellion/src/ai/**`, чистый TS, импортирует только `../schema` (+ чистые хелперы без доступа к state))
- Вход — **только** `CorePlayerView` своей стороны (`toSideView(state, aiSide)`), сложность и seed. Seed = детерминированная функция
  `view.id` + `view.version` (никаких `Math.random`, `Date`).
- `enumerateCandidates(view)` → конкретные команды из шаблонов `legalActions` (ACTIVATE_SYSTEM: пары лидер×система; MOVE_PIECES:
  конечный набор осмысленных подмножеств, удовлетворяющих вместимости; FINISH_ACTIVATION; PASS) с детерминированными id;
  каждый кандидат принимается движком (property-тест).
- `rankCandidates(view, difficulty, seed)` → упорядоченный список; decision point = top-10 (всегда включает завершающее действие
  `PASS` или `FINISH_ACTIVATION`, если оно легально), `fallbackCandidateId` = выбор бота.
- Поведение (детали эвристик — план BE; ниже — проверяемые свойства):
  - **Империя (охота за базой):** знание о базе — только из своего представления (системы, где видны юниты Повстанцев; системы,
    активированные Империей с наземным юнитом без `BASE_REVEALED`, — «проверено»; после `BASE_REVEALED` — известная база).
    Ищет базу активацией непроверенных систем с доставкой наземных войск; после раскрытия стягивает силы в базу.
    easy — выбор с сильной случайностью (seeded) и ранним пасом; normal — жадный поиск; hard — жадный поиск с координацией
    (максимальная доставка, без пустых активаций, приоритет непроверенных систем рядом со своими силами).
  - **Повстанцы (выжидание + PO-1):** easy — часто уводит юниты из базы (рейды/«расширение»), может оставить её пустой;
    normal — обычно держит охрану, но иногда (seeded) выводит последние юниты из базы под угрозой (имперские наземные силы рядом);
    hard — **никогда** не оставляет базовую систему без юнита Повстанцев (инвариант).
- Сложность берётся из `state.settings.aiDifficulty` (публичная настройка).

### 6. Frontend (`apps/web`, Rebellion core-v1 + platform session host)
- Подписи «AI Commander ещё не реализован» заменены: в шапке/сайдбаре AI-стороны — «AI Commander · бот · сложность X» или
  «AI Commander · OpenAI» (из `automation.strategy` и публичных настроек).
- Во время запроса команды/запуска: индикатор «AI ходит…» (кнопки действий заблокированы).
- После ответа: краткая сводка «Ход AI: N действий» + записи журнала AI-ходов как у человека с пометкой «(AI)» (из уже
  отредактированных событий; для Империи ходы в/из базы показываются как «скрытая зона»); при `fallbacks > 0` и strategy `openai` —
  «часть ходов сделал бот (OpenAI недоступен)».
- `automation.pending === true` после загрузки/ответа → клиент вызывает `POST …/automation/run` (не чаще 1 раза на загрузку/ответ,
  кнопка «Продолжить ход AI» при ошибке).
- ru/en; hot-seat UI без изменений; ничего нового в production-бандле из `@bga/game-rebellion/ai|rules|server`.


## Поправки по официальному запросу PO (2026-11-19, `request.md` → «Официальный запрос PO»; имеют приоритет над Contract выше)
- **D-PO-1 (состояние для модели, п. 3.2):** `AutomationDecisionPoint` получает поле `situation: string` (≤ 4000 символов, англ.) —
  компактное описание игры **с точки зрения актёра**, построенное игрой только из `toSideView(state, aiSide)` (раунд, время/репутация,
  свои силы по системам, видимые силы соперника, известная/неизвестная база, свои лидеры в пуле/на поле, текущая активация). Полный
  внутренний state модели не отправляется никогда. Для AI-Империи до раскрытия базы `situation` не содержит базовой системы (тот же
  инвариант, что для кандидатов). Промпт: короткие инструкции — роль фракции, цель, правила видимости, «выбери один id из списка;
  правила проверяет движок», поля = данные.
- **D-PO-2 (защищённый идентификатор, п. 3.2):** модель возвращает только `selectedActionId` из enum id кандидатов (+ `reason`);
  параметры команды берутся сервером из кандидата, модель параметров не передаёт. id кандидата — непрозрачный, не содержит систем/юнитов.
- **D-PO-3 (причина fallback в диагностике, п. 6–7):** `AutomationRunSummary` получает `fallbackReasons: string[]` — уникальные коды
  (`AI_TIMEOUT`, `AI_RATE_LIMITED`, `AI_PROVIDER_ERROR`, `AI_INVALID_DECISION`, `AI_NOT_CONFIGURED`, `AI_BUDGET_EXCEEDED`,
  `AI_DEADLINE`); коды не секретны. UI при fallback показывает короткую причину по коду (ru/en). Причины также в серверном логе и `AiUsage`.
- **D-PO-4 (какой провайдер активен, п. 7):** `SessionResponse.automation.strategy` и метка в UI (бот/OpenAI); выбор провайдера
  пользователем недоступен (PO-2) — только показ.
- **D-PO-5 (обе фракции, п. 2):** e2e и интеграционные сценарии обязательны для обоих вариантов — человек-Повстанцы vs AI-Империя (сценарий
  PO по умолчанию, сложность Normal) и человек-Империя vs AI-Повстанцы; полный цикл до конца партии — интеграционным тестом (API) для обоих.
- **D-PO-6 (сохранение/перезапуск, п. 2.9, п. 5):** интеграционный тест: прерванный цикл AI (лимит шагов/ошибка) → новый экземпляр приложения
  на той же БД → GET даёт `automation.pending: true` → `automation/run` доигрывает; повтор того же запроса/двойное нажатие (тот же
  `expectedVersion`) не даёт двойного хода (409, AI не ходит дважды).
- **Карта обязательных тестов PO (п. 8) → AC:** 1→AC-03; 2→AC-09 (OpenAI на fake fetch/mock); 3→AC-09; 4→AC-04; 5→AC-02 (AI не ходит
  за человека: `origin 'auto'` только за AI-сторону, человек не может слать команды за AI-сторону); 6→AC-02/AC-07 (D-PO-6); 7→AC-09;
  8→AC-09; 9,10→AC-08 (D-PO-5); 11→AC-07 (D-PO-6); 12→AC-07/AC-08; 13→AC-07 (лимит шагов) + AC-09 (бюджет, дедлайн); 14→AC-11
  (+ env: `bot` без ключа, `OPENAI_ENABLED=false`).
- **Отчёт (п. 11):** `delivery-report.md` дополнительно содержит: что реализовано, архитектурные решения, добавленные тесты, результат
  `pnpm verify`, работает ли реальный OpenAI (AC-12), ограничения, рекомендация следующей задачи.

## Acceptance criteria (testable)
- **AC-01:** (платформа game-agnostic) контракт автоматизации в `@bga/platform` и цикл в `apps/api` не содержат понятий Rebellion
  (архитектурный тест/скан как в SWR-003/005B); `automation` у `ServerGameModule` необязателен; Forbidden Stars и mock-v1 сессии
  дают `pendingActor = null` / `automation.strategy = null` и работают как раньше.
- **AC-02:** (тот же путь команд) каждый ход AI — команда `CommandEnvelope{actor: AI-сторона, expectedVersion, command}` через
  `applyCommand` движка (`origin 'auto'`), `version + 1`, события в журнале состояния и в `SessionEvent`; каждый шаг — отдельный
  commit с оптимистичной конкуррентностью; параллельные запуски по одной сессии не применяют ход дважды и не дублируют вызовы
  провайдера (интеграционный тест).
- **AC-03:** (только своё представление и legal actions) бот и decision point получают только `toSideView(state, aiSide)`; каждый
  кандидат принимается движком (property-тест на seeded-партиях); модель выбирает только id из кандидатов, иначе бот.
- **AC-04:** (скрытая информация) решения AI-Империи до раскрытия не зависят от положения базы (тест: состояния, различающиеся только
  базой → одинаковые decision points/ходы); промпты и логи AI-Империи не содержат id базовой системы и `sessionId` (скан/снапшот на
  seeded-партиях); ответы человеку-Империи не раскрывают базу (существующие сканы SWR-005 зелёные с AI-ходами Повстанцев).
- **AC-05:** (детерминизм бота) одинаковые `sessionId` + одинаковые команды человека → побайтно одинаковые журнал и состояние;
  в боте нет `Math.random`/`Date`/`crypto` (ESLint/скан).
- **AC-06:** (сложность — поведение) на фиксированном наборе seeded-партий метрики различаются по сложности (пороги — в
  `test-cases.md`): hard-Повстанцы никогда не оставляют базу пустой; easy-Повстанцы оставляют её пустой хотя бы в части партий;
  Империя hard раскрывает базу в среднем не позже, чем easy (или чаще в пределах N раундов).
- **AC-07:** (цикл в потоке сессии) после команды человека / создания партии с AI первым сервер выполняет шаги AI до хода человека

  ходы и идемпотентен; GET сообщает `automation.pending`.
- **AC-08:** (достижимость исходов) seeded-партии через API/движок доходят до конца: человек-Повстанцы (пасы) vs AI-Империя →

  одной фиксированной партии каждой сложности; hard → инвариант охраны базы держится всю партию.
- **AC-09:** (OpenAI-стратегия) включается только `AI_COMMANDER_PROVIDER=openai` + `OPENAI_ENABLED=true` (иначе старт падает с

  `fallbacks` и `AiUsage`/лог фиксируют код; бюджет по `sessionId` не превышается; ни один автотест не ходит в сеть (fake fetch / mock).

## Assumptions
- A-1: OpenAI выбирает среди top-10 кандидатов бота (а не среди всех ~100 комбинаций «лидер×система» и подмножеств юнитов) — так
  модель никогда не «изобретает» команду и укладывается в лимит 2..10 действий SWR-005B. Это осознанное ограничение v0.
- A-2: Шаги AI выполняются синхронно в HTTP-запросе человека (бот — миллисекунды; OpenAI — ограничено дедлайном, затем бот). Фоновые
  очереди не вводятся (стек). Каждый шаг — свой commit, поэтому прерывание не теряет ход человека.
- A-3: Seed бота — функция `sessionId` и `version` (воспроизводимость партии); случайность «seeded» — только детерминированный хэш.
- A-4: Миграция БД не ожидается (используется существующая `AiUsage`); если понадобится — копия `dev.pre-swr006.db` до миграции.
- A-5: Решения PO-1/PO-2 (`request.md`) — часть спецификации; выбор стратегии в UI вне задачи.
- A-6: Живой вызов OpenAI (AC-12) делает Analyst на BUSINESS_VALIDATION только после отдельного «да» PO в чате.
- A-7: Тексты для модели (summary/objective) — на английском, UI-тексты — ru/en.

## Risks
- Утечка скрытой базы в AI-Империю через кандидаты/summary/лог → decision point только из `toSideView`, тест инвариантности к базе,
  скан промптов.
- Самоблокировка (бот выбирает только недопустимое/зацикливание) → каждый кандидат из legal actions, лимит шагов, завершающее
  действие всегда в списке, property-тест «партия заканчивается».
- Медленные OpenAI-ходы → дедлайн запуска, затем бот; UI-индикатор.
- Расходы → бюджет по `sessionId` (существующий резерв худшего случая), откат на бота без вызова после исчерпания.
- Большой объём правок тестов SWR-005 (авто-пас внутри `applyCommand`) → BE-lead планирует миграцию тестов явно.

## Out of scope
См. `request.md` → `out_of_scope`. Также: обучение/оценка силы бота против людей, объяснения модели игроку (поле `reason` в UI не
показывается), смена правил `core-v1`.
