  есть её наземный юнит (`revealsBaseNow`). Официально (RR p.11, LTP p.12; записи `rebellion:base.reveal-condition`,
  `rebellion:base.reveal-timing`, `rebellion:command.activate.steps`): база раскрывается, если у Империи **когда-либо** есть
  лояльность или наземные юниты в системе базы; после движения — по окончании всего движения активации и до боя (шаг 3 из 5).

## Business goal

AI Commander принимает решения с опорой на проверенные правила, переданные компактно и без утечки скрытой информации;
игровой движок по-прежнему единственный арбитр легальности и централизованно поддерживает инвариант раскрытия базы;
эффект правил на качество/стоимость/задержку измерен воспроизводимо; механизм годится для второй игры.

## Scenarios

- **S-1 (AI с правилами).** Партия «человек против AI», `AI_COMMANDER_PROVIDER=openai`, правила включены: на каждом шаге с
  ≥ 2 кандидатами модель получает Game-блок SWR-006 + блок правил (ID и текст) для фазы, типов кандидатов и стороны AI;
  ответ проверяется как раньше.
- **S-2 (A/B).** `AI_COMMANDER_RULES_CONTEXT=off` → промпт побайтно как в SWR-006 (контрольная группа).
- **S-3 (большой промпт).** Оценка промпта превышает лимит → сначала урезается/снимается блок правил; если всё ещё больше
  лимита — шаг играет бот с кодом fallback; бюджет партии не растёт.
- **S-4 (Империя ищет базу).** Империя вводит наземные войска в систему базы → база раскрывается ровно один раз в официальный
  момент (после всего движения активации), затем проверяется победа Империи.
- **S-5 (benchmark).** Разработчик запускает набор сценариев в режиме mock (CI) или real (явный флаг, лимит $), получает
  отчёт с метриками для `bot`, `openai-no-rules`, `openai-rules`.
- **S-6 (dev-диагностика).** В dev-режиме видно, сколько правил получил AI, их ID, размер контекста в токенах, стоимость, fallback.

## States / rules / exceptions

### R-1. Схема доступа к контексту (информационная безопасность)

| Класс данных | Пример | Может попасть в запрос к OpenAI? |
|---|---|---|
| C1 публичные правила игры | записи KB, версия набора правил | да (отбор — только по C2/C3-метаданным ниже) |
| C2 публичное состояние партии | раунд, фаза, видимые юниты | да, через `situation` из представления стороны AI |
| C3 приватное состояние своей стороны | своя база (для Повстанцев) | да, как в SWR-006 (только для своей стороны) |
| C4 скрытое состояние соперника | база Повстанцев для Империи до раскрытия | **нет** — ни напрямую, ни через выбор правил |
| C5 внутренняя диагностика сервера | `sessionId`/`budgetKey`, бюджет, ключи, ошибки | **нет** |

Вход отбора правил (`RulesSelectionInput`) строится **только** из провалидированного `AutomationDecisionPoint`
(сторона, фаза, типы кандидатов) плюс необязательных «тегов решения», которые игра выводит из представления стороны AI
(C2/C3). Полное состояние в отборщик не передаётся (ограничение на уровне типов, не соглашение).

### R-2. Отбор правил

Детерминированный, без сети и без LLM: (1) обязательные записи движка (`engine scope` — какие механики не реализованы,
решение F-7); (2) `ai: 'core'` (цели, победы, раскрытие базы); (3) записи по типам кандидатов; (4) по фазе; (5) по тегам
решения; фильтр по стороне; внутри группы — `id asc`; обрезка целыми строками по `maxChars`. `needs-review` по умолчанию
**исключаются** из AI-контекста (не становятся авторитетными инструкциями). В промпте правило явно подчинено движку:
«legal actions уже проверены движком; правила — пояснение; механики, которых нет в availableActions, не исполнять».

### R-3. DISC-009 — условие и момент раскрытия

- **Условие (core-v1):** база не раскрыта, партия не закончена, в системе базы есть юнит Империи с
  `unitTypeRevealsRebelBase` (наземный). Лояльности в core-v1 нет (DISC-005) — часть «loyalty» условия документируется как
  неприменимая, точка расширения оставлена.
- **Момент:** проверка централизована (одна функция «state checks» в конвейере применения команды `core-v1`, после каждой
  принятой команды, а также при создании партии). Пока идёт активация Империи (шаг движения не завершён), раскрытие
  откладывается; оно происходит в первый момент, когда движение активации завершено (`FINISH_ACTIVATION`), либо сразу,
  если условие возникло вне активации Империи (будущие механики: развёртывание, миссии).
- **Порядок событий:** `ACTIVATION_FINISHED → BASE_REVEALED → GAME_OVER` (как Q-41 SWR-005); победа Империи проверяется
  после раскрытия и после каждого `MOVE_PIECES` (как раньше).
- **Идемпотентность:** при `revealed = true` проверка ничего не делает; `BASE_REVEALED` в журнале не более одного раза.
- **Скрытость:** до законного раскрытия представление Империи, ошибки и legal actions не зависят от того, где база.

## Acceptance criteria (testable)

- **AC-1:** (workflow) `docs/tasks/SWR-008/` содержит все артефакты этапов; `node scripts/check-task.mjs docs/tasks/SWR-008` → exit 0.
- **AC-2:** (универсальный контракт) В `packages/platform` есть game-agnostic контракт Rules Context для игровых модулей:
  версия набора правил (детерминированный хэш содержимого или явная версия), функция отбора по `RulesSelectionInput`,
  результат `{ text, ruleIds, truncated, rulesVersion }`; модуль игры без базы знаний (Forbidden Stars) работает без правил.
  Ни одного импорта Rebellion в общий код сервера AI. Документ `docs/architecture/rules-knowledge.md` обновлён.
- **AC-3:** (интеграция) При `AI_COMMANDER_PROVIDER=openai` и включённых правилах каждый запрос модели содержит блок правил
  с ID `[rebellion:...]`, отобранный для текущей точки решения; база знаний загружается один раз при старте сервера и
  валидируется (ошибка данных → сервер не стартует). При `AI_COMMANDER_RULES_CONTEXT=off` промпт побайтно равен SWR-006
  (snapshot-тест).
- **AC-4:** (контекстный и ограниченный отбор) Тестами подтверждено: для разных фаз/наборов типов кандидатов/сторон
  выбираются разные релевантные записи; состав и порядок воспроизводимы (одинаковый вход → одинаковые байты); длина блока
  ≤ сконфигурированного лимита (по умолчанию ≤ 6000 символов); никогда не передаются все 181 запись; при переполнении
  отбрасываются целые строки в предсказуемом порядке приоритетов.
- **AC-5:** (статус правил и возможности движка) Записи `needs-review` не попадают в AI-контекст по умолчанию (тест);
  контекст содержит пометку о нереализованных механиках core-v1 (бой, миссии, производство, зонды, лояльность), решение
  F-7 зафиксировано; текст инструкций подчиняет правила legal actions движка.
- **AC-6:** (скрытая информация) (a) Для обеих сторон: два состояния, отличающиеся только скрытым состоянием соперника при
  одинаковом представлении стороны AI, дают побайтно одинаковый полный запрос к провайдеру (instructions + input + schema);
  (b) скан всех запросов mock-провайдера в автоматических партиях за Империю до раскрытия не находит id/названия системы базы
  и других секретов; (c) `sessionId`/`budgetKey` не попадают в запрос; (d) диагностика в UI не показывает скрытых данных.
- **AC-7:** (движок — единственный арбитр) AI по-прежнему выбирает только id из кандидатов: ответ модели с несуществующим id,
  с «новым» типом действия или с текстом правила вместо id → fallback бота; применённая команда всегда проходит полный
  конвейер `applyCoreCommand`. Тесты с враждебными ответами mock-провайдера при включённых правилах.
- **AC-8:** (DISC-009 исправлен) Проверка раскрытия централизована (одна точка в конвейере `core-v1`), соответствует R-3;

## Assumptions

- **A-1.** `needs-review` исключаются из AI-контекста целиком (а не только помечаются) — самый безопасный вариант
  «не авторитетны»; Rules Assistant (будущее) может показывать их с пометкой.
- **A-2.** Лояльности нет в core-v1, поэтому условие раскрытия реализуется для наземных юнитов; «loyalty» — задокументированная
  точка расширения, не реализуется (запрещено §6 запроса: не делать крупных механик).
- **A-3.** Момент раскрытия внутри активации Империи = завершение шага движения = `FINISH_ACTIVATION` (в core-v1 нет боя,
  после которого нужно было бы раскрывать «до боя»); вне активации — сразу. Наблюдаемое поведение core-v1 не меняется
  (подтверждается существующими тестами), меняется структура и гарантия.
- **A-4.** Правила включены по умолчанию для `openai`-стратегии (`AI_COMMANDER_RULES_CONTEXT=on`); бот правил не использует.
- **A-5.** Метрики в benchmark — по документированной рубрике сценариев; токены правил в статистике — фактическая разница
  usage (real) и оценка по символам (mock).
- **A-6.** Модель — та же, что настроена в SWR-006 (`AI_COMMANDER_MODEL_ROLE`); новых моделей/API не вводим.
- **A-7.** Если для учёта затрат нужна миграция `AiUsage` — она допустима (резервная копия `apps/api/prisma/dev.pre-swr008.db`
  сделана), с тестом миграции на копии старой БД.

## Risks

- **RK-1.** Эффект правил может быть нулевым/отрицательным (кандидатов ≤ 10, бот уже ранжирует) — отчёт обязан это показать.
- **RK-2.** Шум real-прогона при малом бюджете — повторы и интервалы, вывод только при устойчивой разнице.
- **RK-3.** Утечка через «теги решения» — теги только из представления стороны AI, тест (AC-6a) на неизменность запроса.
- **RK-4.** Хрупкость io-проверок покрытия KB (имена файлов/символов) при рефакторинге раскрытия — обновлять evidence.
- **RK-5.** Рост промпта выталкивает бюджет партии быстрее — измерить и отразить; лимит не повышать.

## Out of scope

Бой, миссии, производство, зонды, лояльность, дополнения; полноценный Rules Assistant и HTTP-эндпоинты поиска правил;
редизайн UI; новые модели/замена API; RAG/векторные БД/микросервисы; правила Forbidden Stars; повышение бюджета партии.

## Analyst decisions on QA questions (EARLY_QA_DESIGN, `test-cases.md` Q-1..Q-12)

- **QD-1 (Q-1).** Да: при уже выполненном условии (искусственные состояния) раскрытие происходит в первой точке проверки,
  где не идёт активация Империи — т.е. на `FINISH_ACTIVATION` любой системы, либо сразу после команды вне активации Империи.
- **QD-2 (Q-2).** Да: проверка после **каждой** принятой команды (включая `ACCEPT_HANDOFF`, `PASS`, конец раунда) и при
  создании партии; она идемпотентна и дешёвая.
