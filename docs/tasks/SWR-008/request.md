## Запрос PO (дословно)

SWR-008 — Rules Integration & Game Integrity. Проект: `dimatitov/bga`. Приоритет: High. Тип: AI / Game Core / Rules Quality. Зависимости: SWR-005C, SWR-006, SWR-007.

1. Контекст. Мы разрабатываем универсальную платформу для игры против ИИ в физические настольные игры. Первая поддерживаемая игра — Star Wars: Rebellion. Следующая — Forbidden Stars. В предыдущих итерациях реализованы: SWR-005 — первый срез настоящих игровых правил; SWR-005B — серверная интеграция OpenAI; SWR-005C — база знаний правил Rebellion; SWR-006 — AI Commander с deterministic и OpenAI-провайдерами; SWR-007 — модернизация технического стека и CI. По отчёту SWR-005C база содержит 181 запись правил, механизм поиска и функцию `buildRulesContext`. Аудит выявил DISC-009: раскрытие базы проверяется только при завершении активации Империи. Перед началом разработки проверить актуальные статусы и фактическую реализацию всех зависимостей. Не считать сведения из этого задания более достоверными, чем текущий код и принятые delivery reports.

2. Цель. Обеспечить согласованность между игровым движком, базой знаний правил и AI Commander. После SWR-008: 1) OpenAI Commander использует релевантные правила при принятии решений; 2) правила передаются компактно, с учётом фазы и доступных действий; 3) AI не получает скрытую информацию соперника; 4) DISC-009 исправлен на уровне игрового движка; 5) есть измеримые результаты влияния Rules Context на качество решений, стоимость и задержку; 6) реализация остаётся расширяемой для других игр.

3. Перед началом. Используй существующую агентную систему, роли, workflow, документы задач и процедуру приёмки. Изучи: `docs/tasks/SWR-005C/`, `docs/tasks/SWR-006/`, `docs/tasks/SWR-007/`, архитектурный blueprint, механизм `buildRulesContext`, реализацию AI Commander, контракты `PlayerView` и `legalActions`, систему хранения и изменения состояния, аудит DISC-009 и связанные правила, существующие автоматические проверки скрытой информации. Создай документацию SWR-008 в принятой структуре проекта. Не начинать реализацию до анализа зависимостей и фиксации критериев приёмки.

4. Rules Context для OpenAI Commander. 4.1 Подключение: интегрировать `buildRulesContext` в существующий pipeline выбора действий OpenAI Commander. Предполагаемая схема: Game State → PlayerView → Legal Actions → Rules Selection → AI Prompt → AI Decision → Validation → Command API. Приоритет — повторное использование существующих интерфейсов. 4.2 Выбор правил: не передавать модели все 181 правило при каждом ходе. Система должна выбирать релевантные записи по: текущей фазе игры; доступным типам действий; стороне игрока; действующим ограничениям; условиям победы; контексту конкретного решения, если его безопасно использовать. Добавлять краткие идентификаторы правил для диагностики. Если релевантных записей слишком много, использовать предсказуемую приоритизацию и ограничения размера контекста. Учитывать `needs-review`: неподтверждённые записи не должны автоматически становиться авторитетными инструкциями. 4.3 Разделение ответственности: Game Core — единственный источник истины о допустимости действий. Rules Context предназначен для объяснения и улучшения принятия решений, а не для определения легальности действий. AI не может: создавать новые типы действий; обходить `legalActions`; самостоятельно применять игровые эффекты; изменять правила; получать приватное состояние соперника. Текст правил не должен противоречить текущим возможностям движка. Если официальная механика ещё не реализована, AI не должен пытаться её выполнить.

5. Безопасность информации. Разработать и проверить строгую схему доступа к контексту. Различать: публичные правила игры; публичное игровое состояние; приватное игровое состояние своей стороны; скрытую информацию противника; внутренние диагностические данные сервера. Общие правила являются публичными, но выбор конкретного фрагмента правил тоже не должен раскрывать секретное состояние. Например, нельзя выбирать правило для AI-Империи на основании того, где в действительности расположена скрытая база Повстанцев, если Империя этой информации не знает. Rules Context должен формироваться только из разрешённого представления игрового состояния и безопасных метаданных. Добавить тесты отсутствия скрытой информации во всех отправляемых OpenAI данных.

6. Исправление DISC-009. Изучить официальные правила и существующий аудит DISC-009. Текущий недостаток: проверка раскрытия базы привязана к завершению активации Империи. Необходимо: 1) определить точные игровые условия раскрытия базы на основании проверенных правил; 2) найти все изменения состояния, способные повлиять на эти условия; 3) обеспечить проверку инварианта после каждого релевантного изменения; 4) избежать дублирования эффекта раскрытия; 5) сохранить корректную последовательность игровых событий; 6) проверить взаимодействие с условиями победы; 7) исключить утечки скрытой информации до законного раскрытия. Предпочтительно централизовать проверку инвариантов, а не добавлять случайные проверки в отдельных обработчиках команд. Не раскрывать базу после любого перемещения автоматически. Раскрытие должно происходить только при выполнении официальных условий, в правильный момент игрового процесса. Не реализовывать в рамках DISC-009 отсутствующие миссии или другие крупные механики.

7. Оценка качества AI. Нужно не просто подключить Rules Context, а проверить его пользу. Создать набор воспроизводимых игровых ситуаций для существующего среза правил. Сравнить: OpenAI Commander без Rules Context; OpenAI Commander с Rules Context; Deterministic Commander как бесплатную контрольную стратегию. Проверять: долю валидных решений; частоту необоснованного PASS; соответствие решений целям стороны; выбор действий в заранее определённых тактических ситуациях; число fallback; затраты токенов; стоимость запросов; задержку ответа. Нужны сценарии как для Империи, так и для Повстанцев. Для оценки качества создать документированные критерии, а не использовать субъективное «модель стала умнее». Не считать одну победу или небольшое количество случайных игр доказательством улучшения. Не обещать обязательного улучшения: если Rules Context не даёт измеримого эффекта, отразить это в отчёте.

8. Контроль расходов. Сохранить существующий бюджетный механизм SWR-005B/006. Добавить: ограничение размера Rules Context; учёт дополнительного объёма токенов; статистику стоимости решения с правилами и без них; защиту от чрезмерно больших промптов; корректный fallback, если запрос не может быть выполнен в рамках бюджета. Не увеличивать бюджет партии автоматически. Большинство тестов должны использовать mock-провайдер. Реальные OpenAI-вызовы только в ограниченном, явно управляемом smoke/evaluation-сценарии.

9. Архитектура для нескольких игр. Не размещать общие механизмы Rules Context непосредственно внутри Rebellion Commander, если их можно сделать универсальными без избыточной абстракции. Предусмотреть контракт для будущих игровых модулей: получение релевантных правил; формирование безопасного контекста; передача контекста AI; версионирование набора правил. При этом не реализовывать правила Forbidden Stars. Не создавать преждевременно сложную RAG-инфраструктуру, векторную базу или отдельный микросервис. Для текущего объёма базы достаточно существующего поиска, если он соответствует требованиям.

10. Тестирование. Обязательные сценарии: 1) правила выбираются для текущей фазы и допустимых действий; 2) контекст ограничен по размеру; 3) порядок и состав правил воспроизводимы; 4) AI получает правила нужной игры; 5) публичные правила не приводят к утечке скрытого состояния; 6) изменение скрытого состояния противника при неизменном PlayerView не изменяет отправляемый контекст; 7) AI по-прежнему выбирает только допустимые действия; 8) при пустом Rules Context игра продолжает работать; 9) OpenAI недоступен — deterministic fallback работает; 10) бюджет партии соблюдается; 11) DISC-009 корректно обрабатывает каждый применимый переход состояния; 12) раскрытие базы не происходит преждевременно; 13) раскрытие не повторяется; 14) условия победы остаются корректными; 15) сохранение и восстановление партии работает; 16) все существующие тесты проходят. Выполнить `pnpm verify`, `check-task` и необходимые проверки CI.

11. Интерфейс. Не создавать полноценный Rules Assistant. Допускается небольшое улучшение dev-диагностики: сколько правил получил AI; какие ID правил использованы; сколько токенов занял контекст; сколько стоил запрос; был ли fallback. Не отображать пользователю скрытые данные из AI-диагностики.

Критерии приёмки: SWR-008 оформлена по workflow проекта; `buildRulesContext` интегрирован с AI Commander; отбор правил контекстный и ограниченный; защита приватной информации подтверждена тестами; Game Core остаётся единственным арбитром правил; DISC-009 исправлен и покрыт тестами; есть воспроизводимый benchmark AI с правилами и без; измерены стоимость и задержка; fallback и бюджет работают; универсальный интерфейс готов к расширению; `pnpm verify` проходит; ревью, QA и delivery-report завершены.
