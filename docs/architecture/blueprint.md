# Star Wars: Rebellion AI — архитектура проекта и план внедрения агентной разработки

**Версия:** 0.1 (проектный blueprint)  
**Назначение:** передать Claude/Codex как технический план и основу для реализации.  
**Первый приоритет:** наладить систему агентов разработки, затем построить первый сквозной сценарий приложения.  
**Язык рабочих документов:** русский (имена файлов, интерфейсы, код — английский).

> Это план, а не утверждение, что инфраструктура или приложение уже реализованы. Перед внедрением проверить актуальный формат конфигурации и доступность multi-agent/subagent-функций в используемой версии Codex. Если агентные функции ограничены, сохранить роли и контракты, а исполнение организовать через доступные механизмы без имитации параллелизма.

> **Примечание (2026-11-08, SWR-003):** структура пакетов из §7 заменена мультиигровой: `@bga/platform` + `packages/games/<id>` (см. `docs/architecture/application.md`, `docs/architecture/adding-a-game.md`). Остальной документ — исходный целевой план.

## 1. Цель продукта

Веб-приложение-компаньон для физических партий **Star Wars: Rebellion**, позволяющее играть одному против AI-соперника за любую из сторон: Империю или Повстанцев.

- Визуальная интерактивная 2D-карта галактики с системами, юнитами, лидерами и жетонами.
- Выбор, drag-and-drop и действия через понятный интерфейс; поддержка мыши и, позднее, сенсорного ввода.
- Синхронизация виртуальной и физической партии: пользователь отражает на экране действия, совершаемые за столом; приложение предлагает и фиксирует ходы бота.
- Единый движок правил и проверка действий человека и AI.
- Строгое разграничение скрытой информации (в первую очередь расположения базы Повстанцев, секретных карт и намерений).
- Сохранение/восстановление партии, журнал событий, возможность воспроизвести проблемную последовательность ходов.
- Выбор сложности AI в перспективе.
- Поддержка дополнений в будущем, **не в первом MVP**.

### Границы начального MVP

Первый MVP **не обязан** играть полноценную партию Rebellion. Его цель — доказать работоспособность агентного процесса разработки и вертикального среза: от отображения карты до валидируемого действия, сохранения и автоматических тестов. Визуальные и игровые данные на этом этапе могут быть временными/тестовыми.

Отдельно проверять права на использование изображений поля, текстов карт и иных материалов правообладателей до публичного распространения; для прототипа не включать чужие ассеты в открытый репозиторий без разрешения.

## 2. Две независимые архитектуры

1. **Development Agent Team** — Claude/Codex-агенты, разрабатывающие код, планирующие задачи, выполняющие проверки, проводящие ревью, тестирование и бизнес-приёмку.
2. **Game AI Engine** — runtime-система выбора ходов внутри веб-приложения через OpenAI API. Она не должна зависеть от системы агентов разработки.

Сначала реализуем Development Agent Team. Игровой AI добавляется после базового движка состояния и действий.

## 3. Зафиксированный технологический стек

| Назначение | Технология | Комментарий |
|---|---|---|
| Клиент | React + TypeScript + Vite | SPA, без React Native и SSR |
| UI | MUI | Базовые интерфейсные элементы |
| Локальный UI-state | Zustand | Выделения, инструменты, модальные окна, viewport |
| Серверный state | TanStack Query | Запросы и кеширование |
| 2D-игровое поле | React Konva | Canvas-слои, pan/zoom, drag-and-drop |
| API | Node.js + NestJS | Модули с явными границами |
| Контракты | TypeScript + Zod | Общие схемы и runtime-валидация |
| Сохранения | SQLite + Prisma | Удобно для локального MVP; можно мигрировать |
| Игровые решения | OpenAI Responses API | Только через сервер, с журналированием затрат |
| Unit/integration | Vitest | Прежде всего детерминированный game-core |
| E2E | Playwright | Браузерные сценарии, скриншоты, traces |
| Monorepo | pnpm workspaces | apps и packages |
| Качество | ESLint, Prettier, TypeScript strict | Автоматические проверки |

Не добавлять Redis, микросервисы, Kubernetes, отдельный event bus, real-time multiplayer или 3D-движок без реальной потребности. Первоначально достаточно REST API и локального сохранения. **Game-core — чистый TypeScript-пакет**, не импортирующий NestJS, React или OpenAI SDK.

## 4. Модель агентной команды разработки

```text
Product Owner (человек)
  └─ Analyst / Orchestrator
       ├─ Frontend Lead
       │    ├─ UI Worker
       │    ├─ Board Worker
       │    └─ State Worker
       ├─ Backend Lead
       │    ├─ API Worker
       │    ├─ Rules Worker
       │    └─ AI Integration Worker
       ├─ Independent Reviewer
       └─ QA Lead
            ├─ Unit/Integration QA Worker
            ├─ API QA Worker
            └─ Browser/E2E QA Worker
                 ↓
       Analyst final business acceptance
                 ↓
             Delivery report
```

**Роли — логические, а не требование запускать 10 процессов на каждую мелочь.** Оркестратор выбирает минимальный состав под конкретную задачу. Reviewer не должен проверять собственные изменения, QA не должен незаметно чинить продуктовый код и объявлять его проверенным.

### 4.1 Analyst / Orchestrator

- Принимает входное задание, проверяет его полноту, определяет бизнес-цель.
- Формализует требования и acceptance criteria как проверяемые утверждения.
- Фиксирует assumptions, risks, out-of-scope и зависимости.
- Разбивает работу на задачи, определяет последовательность, назначает лидов.
- Устанавливает контракты между Frontend и Backend до начала параллельной работы.
- После интеграции проверяет бизнес-сценарий **до QA**, а после QA принимает итог по AC.
- При неуспехе возвращает конкретную задачу с воспроизводимым дефектом.
- Не объявляет завершение без доказательств.

### 4.2 Frontend Lead

- Определяет компонентную архитектуру, доступность интерфейса, состояние и взаимодействия.
- Делегирует независимые задачи FE workers.
- Проверяет TypeScript, визуальное соответствие, производительность на разумном объёме жетонов.
- Интегрирует изменения в FE и проводит ревью.

### 4.3 Backend Lead

- Определяет API, persistence, правила доступа, валидацию команд и обработку ошибок.
- Разделяет game-core, API, AI-provider и базу данных.
- Делегирует независимые задачи BE workers.
- Следит, чтобы OpenAI API ключи никогда не уходили в клиент.

### 4.4 QA Lead

- Получает спецификацию **до реализации** и готовит test design.
- После реализации назначает unit/integration/API/E2E проверки.
- Проверяет позитивные/негативные сценарии, регрессию и соответствие критериям.
- Сохраняет фактические логи, screenshots и Playwright traces.
- Возвращает дефекты с шагами воспроизведения, severity и ожидаемым/фактическим результатом.

### 4.5 Reviewer

- По возможности независим от авторов изменений.
- Проверяет архитектурные границы, безопасность, типы, возможные регрессии, сложность, тестопригодность.
- Не подменяет QA и бизнес-приёмку.

### 4.6 Workers

- Выполняют конкретную ограниченную задачу с указанием владения файлами и ожидаемого результата.
- Не меняют архитектуру, публичные контракты и чужие файлы без согласования с лидом.
- Прикладывают список изменённых файлов, тестов и известных ограничений.

## 5. Входной контракт задачи

Минимально обязательны `title`, `description`, `acceptance_criteria`. Остальные поля добавляются по необходимости.

```yaml
id: SWR-001
title: "Перемещение жетонов между системами"
description: |
  Игрок может визуально перемещать свои жетоны на карте.
business_value: |
  Синхронизировать физическую партию с цифровым состоянием.
acceptance_criteria:
  - "Жетон можно выбрать мышью"
  - "Возможные точки назначения подсвечиваются"
  - "Недопустимое действие не изменяет GameState"
  - "Допустимое действие сохраняется в истории"
  - "После перезагрузки состояние восстанавливается"
constraints:
  - "React + TypeScript; правила не реализовывать в Canvas"
references: []
priority: high
dependencies: []
out_of_scope:
  - "Физика движения"
  - "Мультиплеер"
```

Analyst должен сформировать:
- `specification.md`: сценарии, состояния, бизнес-правила, исключения.
- `implementation-plan.md`: dependency graph, зоны изменений, контракты.
- `test-cases.md` (в сотрудничестве с QA Lead): тестовые сценарии и покрытие AC.

Не превращать некритические неопределённости в бесконечные вопросы: фиксировать разумные допущения в `assumptions` и двигаться дальше. По действительно блокирующим продуктовым вопросам запросить решение человека.

## 6. Workflow задачи и quality gates

```text
INTAKE
  → ANALYSIS
  → TECH_PLANNING + EARLY_QA_DESIGN
  → IMPLEMENTATION
  → INTEGRATION + CODE_REVIEW
  → BUSINESS_VALIDATION
  → QA_EXECUTION
  → FINAL_ACCEPTANCE
  → DELIVERY
```

У каждого этапа: `pending | in_progress | passed | failed | blocked`, ответственный, артефакт, основание решения.

### Обязательные проверки

1. `lint` и `typecheck` — успешно.
2. `unit/integration` — пройдены соответствующие тесты.
3. `build` — успешно.
4. Для изменений интерфейса — браузерные E2E, по необходимости screenshots/traces.
5. Для изменений игрового состояния — tests на переходы, инварианты и ошибочные команды.
6. Все acceptance criteria имеют вердикт и указание доказательства.
7. Независимый reviewer не оставил блокирующих замечаний.
8. Не проверявшиеся сценарии имеют явный статус `not_run`, а не `passed`.

Возврат из QA → ответственному лиду → исправление → повторное тестирование затронутых сценариев и регрессии. При спорном требовании — к Analyst/Product Owner. В отчетах различать **реально выполненные** и **запланированные** проверки.

## 8. Архитектура игрового приложения

```text
React SPA (view + interactions)
       ↓ typed commands / queries
NestJS API (auth later, sessions, validation, persistence)
       ↓
Game Core (pure TS: rules, legal actions, state transitions)
       ↓
Event log + snapshot (SQLite)

AI Decision Service → legal actions + sanitized AI view
       ↓
OpenAI API → structured decision
       ↓
Validate selected action through Game Core
       ↓
Commit event + return UI update
```

### 8.1 Модули клиента

- `GameBoard`: карта/системы и интерактивные Canvas-слои.
- `Selection`: выделение юнитов/лидеров/жетонов.
- `Actions`: доступные команды, подсветка целевых систем.
- `GameSession`: раунд, фаза, сторона игрока, сохранение.
- `AIStatus`: ход ИИ, объяснение действия без раскрытия его секретов.
- `History`: журнал событий и просмотр предыдущих действий.

### 8.2 Canvas / drag-and-drop

React Konva:

```text
Stage
├── MapBackgroundLayer
├── SystemsLayer
├── UnitsLayer
├── LeadersLayer
├── TokensLayer
└── InteractionOverlayLayer
```

- Pan/zoom, hover, select, drag preview, snap к допустимым системам.
- Отрисовка координат — задача UI, **правила перемещения — задача game-core**.
- Drag вызывает команду, а не напрямую мутирует сохранённое состояние.
- Сервер/движок отклоняет недопустимую команду; UI показывает причину и откатывает предпросмотр.
- ИИ и пользователь используют одинаковую модель команд.

```ts
type MoveUnitsCommand = {
  type: 'MOVE_UNITS';
  fromSystemId: string;
  toSystemId: string;
  unitIds: string[];
};
```

### 8.3 Состояние и журнал

Хранить не только текущий `GameState`, но и версии состояния/события для воспроизведения и тестирования. Команда должна быть атомарной; только после валидации коммитится событие и новый state. Не допускать гонок при параллельных запросах (версия состояния / optimistic concurrency).

### 8.4 Скрытая информация

- Полный state доступен только доверенному runtime и persistence.
- Каждый участник (человек, бот) получает собственную `PlayerView`, сформированную из полного состояния.
- Бот за Империю **не видит скрытую базу повстанцев** до легального раскрытия; человек за Империю также не видит её в UI.
- Секретные карты, информация о миссиях и другие закрытые данные фильтруются на сервере, не прячутся CSS-ом.
- В prompts/логах/аналитике не допускать утечек секретных сведений противоположной стороны.

### 8.5 AI decision loop (после MVP)

1. Core вычисляет допустимые действия для текущего состояния.
2. Backend строит безопасное представление информации, доступной AI-стороне.
3. Стратегический сервис ранжирует варианты и запрашивает модель при необходимости.
4. Модель возвращает **строго структурированный выбор** (ID действия + необязательное объяснение).
5. Backend проверяет, что выбор входит в список legal actions.
6. При невалидном результате — ограниченный retry или детерминированный fallback.
7. Команда применяется через Game Core и фиксируется в event log.

Модель не является источником истины по правилам и не должна самостоятельно придумывать новый тип разрешённого действия. Сложность повышать качеством оценки/поиска/планирования, а не только системным промптом.

## 9. Очерёдность реализации

### Этап A — Agent Foundation (первый приоритет)

- Создать базовый репозиторий и `AGENTS.md`.
- Определить роли, полномочия, выходные артефакты и ограничения редактирования файлов.
- Настроить конфигурации/skills для доступной версии Codex.
- Задокументировать dispatch, handoff, retries, escalation и acceptance workflow.
- Проверить workflow на маленькой демонстрационной задаче.

**Definition of Done:** задокументированная, запускаемая система делегирования, которая выдаёт реальные артефакты и не утверждает, что тесты пройдены, если они не запускались.

### Этап B — Quality Gates

- Настроить линтер, typecheck, test, build и E2E команды.
- QA Lead готовит сценарии до реализации.
- Reviewer и QA работают как отдельные роли.
- Стандартизировать `qa-results.md`, `acceptance.md` и ссылки на фактические доказательства.

**Definition of Done:** тестовая задача проходит воспроизводимый lifecycle с проверками и отчётом.

### Этап C — Application Skeleton

- Настроить pnpm monorepo, React/Vite и NestJS.
- Добавить `contracts`, `game-core`, `game-data`.
- Создать health endpoint, простую страницу, минимальный контракт API и сквозной smoke E2E.
- Подключить SQLite/Prisma для сессии и простого состояния.

**Definition of Done:** проект локально запускается, frontend вызывает API, есть сохранение и работающий smoke test.

### Этап D — Вертикальный срез игрового поля

- Нарисовать несколько **тестовых** систем без претензии на полноценную карту.
- Показать жетоны, выделение, drag preview и подсветку.
- Реализовать `MOVE_UNITS` через game-core и API.
- Сохранять событие; восстанавливать состояние после refresh.
- Проверить неправильный ход, rollback/ошибку, UI E2E и unit tests.

**Definition of Done:** действия пользователя проходят весь путь UI → API → rules → persistence → UI, автоматически тестируются и воспроизводятся по журналу.

### Этап E — Данные и правила Rebellion (отдельная серия задач)

- Формализовать реальную топологию карты и типы компонентов.
- Поэтапно реализовывать раунды, фазы, миссии, лидеров, системы, боевые действия и победу.
- Приоритет — тестируемость каждой механики и проверка по правилам оригинальной игры.
- Дополнение Rise of the Empire — после базовой версии.

**Definition of Done:** набор правил проверяется детерминированными сценариями и покрывает согласованную часть игры. Не заявлять «полная поддержка», пока все основные механики не реализованы.

### Этап F — Игровой AI

- Реализовать `PlayerView` и AI legal-actions интерфейс.
- Подключить OpenAI SDK на сервере с конфигурируемой моделью и лимитами.
- Разделить стратегическое планирование и быстрые локальные действия.
- Добавить учёт количества запросов, токенов, стоимости, задержки и ошибок.
- Создать игровые сценарии для AI за Империю и за Повстанцев; проверить отсутствие нечестного доступа к секретам.

**Definition of Done:** бот принимает допустимые действия за обе стороны в покрытых движком сценариях; ошибки модели не ломают состояние игры.

## 10. API и безопасность: ограничения

- API-ключ OpenAI хранится только на сервере (`.env`, секрет-хранилище), не в React bundle.
- Структурированные ответы модели валидируются Zod и сверяются с legal actions.
- Rate limit, бюджет на партию, timeout, retry/fallback, логирование usage.
- Секретная информация не отправляется AI, если она недоступна его игровой стороне.
- При выпуске для других пользователей понадобится auth, изоляция партий и модель оплаты/BYOK с безопасной обработкой ключей — это **не MVP**.
- Не добавлять реальные лицензионные арты/сканы в публичный проект без права на распространение.
